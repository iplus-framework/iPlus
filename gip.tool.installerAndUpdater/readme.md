# gip.tool.installerAndUpdater

Cross-platform installer and updater for **iPlus** and **iPlus-MES**.

The same binary runs on Windows, Linux and macOS. It needs no registry entries,
no environment variables and no administrator rights — everything it writes lives
in the installation folder.

## What it does

1. **Obtains the payload** from one of three sources:
   - a **GitHub release** (downloaded directly from
     `iplus-framework/iPlus` or `iplus-framework/iPlusMES`),
   - a **local zip** file,
   - an already **extracted folder**.
2. **Copies the application files** into the target folder. `ConnectionStrings.config`,
   `UserFiles/` and `Logs/` are never overwritten, so an update keeps the customer's
   data and settings.
3. **Writes `ConnectionStrings.config`** in the V5 format
   (`iPlusV5_Entities` / `iPlusMESV5_Entities`, `providerName="Microsoft.Data.SqlClient"`).
4. **Optionally creates the database** and applies the `initial-install-*.sql`
   script generated by `gip.tool.dbscript`.
5. **Creates a desktop shortcut** — `.cmd` on Windows, `.desktop` on Linux,
   `.command` on macOS.
6. **Optionally starts the application**.

## Release layout it understands

Both layouts produced by `build/publish-release.sh` are supported:

```
iplus-<ver>-desktop-linux-x64.zip        # single platform, files at the root
iplus-<ver>-all.zip                      # combined bundle
  iplus-<ver>-desktop-linux-x64/...
  iplus-<ver>-desktop-win-x64/...
  iplus-<ver>-wpf-win-x64/...
  iplus-<ver>-console-linux-x64/...
```

The platform folder is auto-detected from the running OS and architecture
(`desktop-linux-x64`, `desktop-win-x64`, `desktop-osx-arm64`, …) and can be
overridden in the UI.

## Usage

```bash
# Windows
gip.tool.installerAndUpdater.exe

# Linux / macOS
./gip.tool.installerAndUpdater
```

Then pick the product, the source, the installation folder and the SQL Server
connection, and press **Install / Update**.

## Signing and publisher verification

Windows binaries can be Authenticode-signed so that SmartScreen and the runtime's
publisher verification can tell who built them:

```bash
./build/sign-release.sh --mode self-signed --pfx my.pfx --password '***'
```

In CI the same behaviour is controlled by `SIGNING_MODE=none|self-signed|azure`. See
[docs/release-process.md](../docs/release-process.md#code-signing).

The runtime checks the signer of every assembly it registers
([`TrustedPublisherStore`](../gip.core.licensing/TrustedPublisherStore.cs), called from
`ACClassManager.RegisterAssemblyTypes`). The trusted thumbprints live in
`Licenses/TrustedPublishers.txt` next to the executable. Verification is **off by
default** and fail-open, so an unsigned or unknown assembly still loads unless an
administrator explicitly sets `mode=enforce`.

## Notes

- The installer is **not** shipped as a NuGet package (it is listed in
  `IPlusPackExclude`); it is distributed as a release artifact
  (`iplus-<ver>-setup-win-x64.zip` / `iplus-<ver>-setup-linux-x64.zip`).
- There is **no automatic update mechanism**. Enterprises want to control exactly when
  an update is applied, so the installer is run deliberately by an administrator.
- SQL Server access uses `iPlus.Microsoft.Data.SqlClient`, the same assembly
  identity as the runtime, so no binding redirects are needed.
- `xp_instance_regread` (Windows-only) is no longer used; the default backup
  directory is read through `SERVERPROPERTY('InstanceDefaultBackupPath')`.
- Zip handling uses `System.IO.Compression` instead of DotNetZip, and the
  credential encryption uses `Aes` instead of the obsolete `RijndaelManaged`.
